# Архітектурні рішення (ADR)

> Цей документ пояснює **чому** прийняті ключові рішення.
> Читай перед тим як пропонувати альтернативи — можливо це вже обговорювалось.

---

## ADR-001: Кожен предмет в інвентарі = окремий Entity

**Рішення:** 3 мечі = 3 Entity в БД. 50 стріл = 50 Entity в БД.

**Чому не `quantity` поле в EntityRelation:**
- Потрібна можливість екіпірувати **конкретний** предмет зі "стаку" (один може бути зачарованим)
- Предмет може мати унікальний стан (прокляття, особлива назва, зачарування)
- Архітектурна консистентність — всі зв'язки між Entity

**Стакінг:** тільки візуальний в UI. Якщо Entity не має overrides — вони групуються в стак з лічильником. Реальна кількість окремих записів в БД.

## ADR-002: Інвентар — це EntityRelation, не окрема механіка

**Рішення:** Немає `inventory-v1` механіки. Інвентар реалізується через `EntityRelation` з `key: 'inventory'`.

**Чому:**
- EntityRelation — механізм двигуна для будь-яких зв'язків між Entity
- Виділяти інвентар в окрему механіку надлишково — він не потребує окремих схем чи компонентів
- Механіки **використовують** EntityRelation API, але самі не є EntityRelation

---

## ADR-003: Немає окремої Stats механіки

**Рішення:** Одна механіка `values-v1` покриває всі типи значень через три поля: `static`, `dynamic`, `formula`.

**Чому не розділяти на Stats/Health/Combat:**
- Різниця між STR і HP — тільки в `kind` поля (`static` vs `dynamic`)
- Один інстанс `values-v1` з назвою "health" і інший з назвою "core-stats" — цього достатньо
- Менше коду, більше гнучкості для нестандартних ігрових систем

---

## ADR-004: EntityTrait — Lazy Init (зберігає тільки відхилення)

**Рішення:** EntityTrait зберігає тільки значення які відрізняються від `default` в конфізі MechanicInstance.

**Чому:**
- Якщо майстер додає нове `dynamic` поле після створення Entity — не потрібно мігрувати дані
- При читанні: є в EntityTrait → повертаємо, немає → беремо `default` з конфігу
- Новий Entity автоматично отримує всі поточні дефолти без ініціалізації

---

## ADR-005: Статуси кампанії ігноруються на перших етапах

**Рішення:** Логіка DRAFT/ACTIVE/ARCHIVED і блокування механік при переході — не реалізується до Етапу 4.

**Чому:**
- Блокування залежить від повністю реалізованих механік, формул, валідації
- Реалізовувати це до появи самих механік — передчасна оптимізація
- Поле `status` в БД є, але логіка блокування — пізніше

---

## ADR-006: Формули рахуються на фронтенді (статичні) і сервері (Actions)

**Рішення:**
- Статичні формули (модифікатори, пасивні значення) → **фронтенд**
- Actions з `ROLL` → **сервер**
- Actions що змінюють БД → **сервер**
- Actions з `@target` (приховані дані, Fog of War) → **сервер**

**Чому фронтенд для статичних:**
- Реактивність без round-trip до сервера
- Дані вже є в клієнті після завантаження

---

## ADR-007: Uploadthing для файлів (не власний S3)

**Рішення:** `@uploadthing/nuxt` для завантаження файлів.

**Чому:**
- Офіційний Nuxt модуль, простіша інтеграція
- Безкоштовний план достатній для розробки
- Капотом AWS S3 — при потребі можна перейти на власний S3/R2 замінивши тільки адаптер
- Логіка Media в БД залишається незмінною

---

## ADR-008: sheet-v1 тільки відображає, не зберігає дані

**Рішення:** Sheet механіка зберігає тільки дерево нод (шаблон відображення). Самі дані завжди в values трейтах.

**Чому:**
- Розділення відповідальності: дані ↔ представлення
- Якщо нода посилається на трейт якого немає — попередження, не помилка
- Майстер сам вирішує чи підключати трейт до Asset

---

## ADR-009: Циклічні залежності формул заборонені повністю

**Рішення:** При кожному збереженні формули — DFS перевірка по всіх трейтах кампанії. Якщо цикл — не зберігаємо.

**Чому:**
- В реальних RPG механіках циклічних залежностей між розрахунковими значеннями не існує
- Цикл — завжди помилка дизайну
- Краще заборонити явно ніж отримати нескінченний цикл в рантаймі

---

## ADR-010: DOM замість Canvas на перших етапах

**Рішення:** Перші 5 етапів — DOM-based інтерфейс. Canvas/PixiJS — Етап 6.

**Чому:**
- Верифікуємо архітектуру даних без складності рендерингу
- Canvas — додаткове View яке підключається пізніше
- Менший ризик для MVP

---

## ADR-011: Vertical slices з окремими сервісами доступу

**Рішення:** Бекенд ділиться на вертикальні зрізи по фічах. Правила доступу живуть в окремих
сервісах які повертають **становище** (context object), а не булеве значення. tRPC-роутер —
тонкий, як контролер.

```
server/
├── features/<feature>/
│   ├── domain/        ← чистий TS: без Prisma, без tRPC, без h3
│   ├── services/      ← <feature>-access.service.ts + <feature>.service.ts
│   ├── requests/      ← Zod-схеми входу
│   ├── responses/     ← DTO-мапери
│   └── <feature>.router.ts
├── engine/            ← механіки, формули, Layered State Resolve (чистий TS)
└── infrastructure/
    ├── errors.ts      ← NotFoundError / ForbiddenError / BadRequestError
    └── trpc/          ← context, error-mapper
```

**Правило кожного шару:**

| Шар | Можна | Заборонено |
|---|---|---|
| `<feature>.router.ts` | схема входу, виклик сервісу | `ctx.prisma`, перевірки прав |
| `services/*-access` | резолв доступу, повернення становища | бізнес-правила |
| `services/*` | правила, оркестрація, Prisma | `TRPCError`, `h3` |
| `responses/` | обрізка й перейменування полів | запити до БД |
| `domain/`, `engine/` | чистий TypeScript | Prisma, tRPC, h3 |

**Чому не мідлвари на процедурах:**
- Мідлвар відповідає так/ні і кладе в контекст один ресурс — цього досить для «майстер чи гравець»
- Щойно правило розгалужується (видимість тек, транзитні вузли, гранти) — мідлвар або розбухає,
  або робить запит на кожну перевірку
- Сервіс доступу пише розгалужені правила як звичайний код, без обмежень мідлвара

**Чому становище, а не булеве:**
- `requireCampaign()` повертає кампанію разом із роллю і видимістю того хто питає
- Складність рахується **один раз** і далі відповідає офлайн, без додаткових запитів
- Становище — чистий доменний об'єкт, тестується без бази

**Чому помилки не знають про транспорт:**
- Сервіси кидають `NotFoundError` / `ForbiddenError` / `BadRequestError`
- Єдиний мідлвар мапить їх у коди tRPC; усе інше летить у 500 як справжній баг
- Доменний код не згадує tRPC взагалі

**Чим тримається гарантія що перевірку не забули:**
- Сервіс фічі — єдині двері до даних цієї фічі, і він завжди заходить через свій access-сервіс
- Не типами мідлвара, а дисципліною шарів

**Чому не додаємо repository-шар:**
- Prisma вже є абстракцією над SQL, проєкт сольний
- Додати `repository` можна пізніше, коли конкретний сервіс розбухне

**Наслідок для видимості матеріалів:** зараз гравці бачать усе дерево. Коли знадобляться
таємні нотатки майстра — рішенням буде видача доступу на теку плюс чистий об'єкт видимості
з рівнями `Full` / `Transit` / `None`, де `Transit` дозволяє бачити шлях до відкритої теки,
не показуючи її сусідів. Разом з цим варто перейти на materialized path (`Folder.path` як
масив id від кореня) замість рекурсії по `parentId`: перевірка вкладеності стає операцією
над масивом без запитів до БД.

**Порядок впровадження:**
1. Полагодити `prisma/json-types.ts` (блокує Етап 2)
2. `infrastructure/errors.ts` + error-mapper
3. `features/campaigns/` цілком як пілот
4. `folders/` і `assets/` за зразком
5. Materialized path — окремою міграцією, разом з видимістю матеріалів
6. `engine/` — порожнім перед Етапом 2

## ADR-012: Здібності оголошуються в коді, набір закритий

**Рішення:** Усі назви здібностей (`CampaignAbility`, `MaterialAbility` і майбутні)
живуть у `shared/permissions/` як `as const` масиви. Механіки **не** приносять нові
назви здібностей у рантаймі.

**Чому саме так:**

На цьому тримається вся перевірка прав:

- опечатка `can('materials:writ')` — помилка компіляції з обох боків
- `canOn(folder, 'campaign:update')` відхиляється, бо набір виводиться з суб'єкта
- додали здібність, не розписали по ролях — `Record<Ability, …>` не зійдеться

Щойно набір стає відкритим, тип вироджується в `string` і зникає все перелічене.
Це не компроміс на полях — це втрата єдиного механізму, який тримає клієнт і
сервер узгодженими.

**Чому це не обмежує механіки:**

Механіка приносить **дії** (методи для Actions), а не нові назви прав. Питання
«чи можна виконати цю дію» вирішується наявними здібностями плюс правилами на
сутності — так само, як видимість матеріалів вирішується прапорцем на теці, а не
новою здібністю.

Якщо механіці колись знадобиться справді нова назва права — вона додається в
`shared/permissions/` руками, як звичайна зміна коду.

**Що це виключає:**

Механіки, завантажені як зовнішні пакети в рантаймі. Це узгоджується з тим, що вже
записано: MechanicDef — «оголошена **в коді** логіка», а `values-v1`, `sheet-v1`,
`effects-v1` реєструються в MechanicRegistry на етапі збірки.

Якщо намір колись зміниться — типобезпеку на цій межі доведеться відпустити і
замінити рантайм-валідацією для здібностей стороннього походження. Рішення свідоме,
не випадкове.

**Розглянута альтернатива:** відкритий набір рядків із рантайм-перевіркою реєстром.
Відхилено: переносить помилки з компіляції в рантайм заради розширюваності, якої
поки ніхто не потребує.
