# Термінологія TableTop Engine

> ⚠️ Це найважливіший документ для консистентності коду та комунікації.
> Використовуй саме ці терміни скрізь: в коді, коментарях, PR описах, питаннях.

---

## Офіційні терміни

| Термін | Визначення |
|---|---|
| **TraitDef** | Оголошення набору полів на рівні кампанії. Створює майстер у UI. Має `key` (живе у формулах) і `label` (показується). Приклад: `health` з полями `max_hp` і `hp`. Єдиний спосіб зберігати значення в двигуні. |
| **Тип поля** | Оголошений **у коді** вид значення: `number`, `text`, `boolean`, `formula`. Реєстр `FIELD_TYPES` — єдина точка розширення моделі даних. |
| **Asset** | Шаблон / креслення сутності. Має назву, опціональну картинку (Media), текстовий опис (TipTap). Лежить у Folder, належить Campaign. **Аналог класу в ООП.** |
| **Entity** | Конкретний екземпляр Asset. Живий об'єкт у світі гри з поточним станом. **Аналог об'єкту в ООП.** |
| **AssetTrait** | Зв'язка Asset + TraitDef + статичні дані (JSONB). Характеризує шаблон. Приклад: гоблін має `max_hp = 10`. |
| **EntityTrait** | Зв'язка Entity + TraitDef + дані (JSONB). Тримає дві речі: стан динамічних полів і перевизначення статичних. Приклад: цей гоблін має `hp = 3` і `str = 12` замість шаблонних 8. |
| **EntityRelation** | Зв'язок між двома Entity. Має `key` (тип зв'язку, рядок) і `data` (JSONB з деталями). Механізм двигуна для інвентарю, ефектів, спорядження тощо. |
| **Action** | Декларативний покроковий конфіг прив'язаний до Asset. Виконується на сервері. Описує що відбувається при використанні (атака, зілля, закляття). Entity наслідує Actions через `assetId`. |
| **Sheet** | Шаблон листа персонажа як дерево нод. Нативна сутність двигуна, не механіка. Читає значення з трейтів, сам нічого не зберігає. *(Етап 4)* |
| **Effect** | Активний ефект, що модифікує значення. Нативна сутність двигуна. Застосовується через EntityRelation з `key: 'active_effect'`. *(Етап 5)* |
| **Media** | Окрема сутність для файлів (зображення, документи). Належить Campaign. Зберігається в Uploadthing (AWS S3). На неї посилаються Asset, TipTap контент тощо. |
| **Scene** | Ігрове поле (VTT). *(відкладено до Етапу 6)* |
| **SceneEntity** | Присутність Entity на Scene з координатами. *(відкладено)* |
| **SceneDecoration** | Статичні декорації на Scene. *(відкладено)* |
| **Wizard** | Інструмент покрокового налаштування Entity (наприклад, Character Creation). *(відкладено до Етапу 7)* |

## Стара термінологія — НЕ використовувати

| ❌ Не використовувати | ✅ Замінено на |
|---|---|
| `Token` | `Entity` |
| `Trait` (без префіксу) | `AssetTrait` або `EntityTrait` (залежно від контексту) |
| `Mechanic`, `MechanicDef`, `MechanicInstance` | `TraitDef`. Механік як плагінів немає — ADR-013 |
| `Stats mechanic` | Окремий `TraitDef` з потрібними полями |
| `inventory-v1` (як окрема механіка) | Інвентар — це `EntityRelation` з `key: 'inventory'` |
| `sheet-v1`, `effects-v1` | `Sheet` і `Effect` — нативні сутності, ADR-014 |
| `@self.trait['core-stats'].str` | `@core_stats.str` — ADR-016 |

## Важливі уточнення

### Asset vs Entity
```
Asset  = клас "Goblin"          → шаблон, один
Entity = конкретний гоблін #1   → екземпляр, багато
```

### AssetTrait vs EntityTrait
```
AssetTrait  → static поля           → спільні для всіх Entity цього Asset
EntityTrait → dynamic поля          → стан, існує тільки на Entity
            + перевизначення static → чим цей екземпляр відрізняється
```

### Тип поля vs TraitDef
```
Тип поля = number      → код розробника, незмінний
TraitDef = "health"    → набір полів, створює майстер
TraitDef = "core_stats" → інший набір, той самий двигун
```

### Звернення до значень (ADR-016)
```
@core_stats.str     → поле поточної сутності
#target.combat.ac   → параметр виконання дії
```

### EntityRelation — механізм, не механіка
EntityRelation — це API рівня двигуна. Інвентар, ефекти, спорядження реалізуються через нього,
а не як окремі сутності. Кожен предмет інвентаря — окремий Entity (ADR-001, ADR-002).
