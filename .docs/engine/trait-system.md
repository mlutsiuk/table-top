# Trait система

> Замінює попередній документ про Mechanic як плагін. Підстава — [ADR-013](../architecture/decisions.md)
> і [ADR-014](../architecture/decisions.md).

## Концепція

`TraitDef` — оголошення набору полів на рівні кампанії. Це **єдиний** спосіб зберігати значення
в двигуні. Майстер створює скільки завгодно визначень: `health`, `core_stats`, `identity`.

Визначення нічого не зберігає саме. Значення народжуються там, де воно зустрічається з носієм:

- `AssetTrait` — статичні поля на асеті-шаблоні;
- `EntityTrait` — стан динамічних полів і перевизначення статичних на живій сутності (ADR-017).

Реєстру видів механік **не існує**. Точка розширення — тип поля.

---

## Що оголошує TraitDef

```typescript
{
  key: 'core_stats',        // живе у формулах: @core_stats.str
  label: 'Core Stats',      // показується майстрові
  fields: [
    { key: 'str', label: 'Strength', type: 'number', kind: 'static', default: 10 }
  ]
}
```

`key` окремо від `label` тому, що на ключ посилаються формули, прив'язки нод листа й цілі
ефектів (ADR-016). Перейменування підпису не ламає формули; перейменування ключа — деструктивна
операція.

Імена `target`, `source`, `owner`, `parent` зарезервовані. Ключі з префіксом `_` належать двигуну.

---

## Типи полів

Реєстр `FIELD_TYPES` — це те, що реально росте. Кожен тип володіє двома схемами, які лежать в
одному файлі поруч: схемою **конфігу поля** (що налаштовує майстер) і схемою **збереженого
значення**.

| type | kind | Де зберігається |
|---|---|---|
| `number` | `static` | AssetTrait |
| `number` | `dynamic` | EntityTrait *(Етап 3)* |
| `text`, `boolean` | так само | так само |
| `formula` | — | ніде, обчислюється при читанні *(Етап 3)* |

Деталі й приклади конфігів: [`../mechanics/values-v1.md`](../mechanics/values-v1.md).

## Валідація — два рівні

```
Рівень 1 — Zod (структура):
  Чи є fields масивом?
  Чи кожне поле має key, label, type?
  Чи formula поле не має kind і default?

Рівень 2 — бізнес-логіка:
  Чи немає дублікатів ключів?
  Чи немає циклічних залежностей між formula полями і значеннями ефектів?
```

Другий рівень покриває й ефекти: ефект, значення якого посилається на поле, яке він же
модифікує, — той самий цикл (ADR-015).

## Дії на визначенні

Трейт може нести не лише дані. Але дії бувають двох різних видів, і плутати їх не варто:

- **Операції над власними полями визначення** — `damage`, `heal`, `set` для `health`. Належать
  визначенню, бо переїжджають разом з ним на кожен асет.
- **Дії конкретного асета** — удар мечем із ціллю й кидком. Належать асету.

Межа, яка тримає всю конструкцію: визначення оголошує **дані, які двигун інтерпретує**. Операція
як конфіг — це дані. Метод, у який двигун стрибає, — це плагін, від якого ми відмовились.

Конфіг визначення — об'єкт з ключем `fields`, тому `{ fields, actions }` додається пізніше без
міграції.

## Зміни конфігу — безпечні vs деструктивні

```
Безпечні (без попередження):
  + додати нове поле
  + змінити label
  + змінити default value

Деструктивні (показуємо попередження + підтвердження):
  ⚠ видалити поле
  ⚠ перейменувати key поля
  ⚠ змінити type поля
```

Перейменування ключа має бути **окремою операцією з перенесенням значень**, а не парою
«видалити + додати»: інакше дані гинуть на всіх асетах. Зміна типу поки не попереджає ні про що —
ключ лишається оголошеним, тож перевірка осиротілих ключів його не бачить.

У статусі кампанії `ACTIVE` конфіг заблокований повністю (Етап 4).

## Чого тут немає

- **Хуків.** `onEntityCreated` скасовано: ліниво зрезолвлений дефолт-вираз покриває той самий
  сценарій, не порушуючи Lazy Init (ADR-017).
- **Компонентів у визначенні.** Редактор трейтів — частина застосунку, а не те, що реєструє
  механіка.
- **MechanicRegistry.** Див. ADR-013.
